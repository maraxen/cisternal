# Per-surface plugin option mechanisms (cross-surface plugin config spike)

Question per surface: **Q1** can the plugin manifest declare user options (types, choice list, default)? **Q2** where does a saved value persist? **Q3** which processes can read it (MCP server, hooks, agent shell)? **Q4** can it be set non-interactively?

Baseline (Claude Code, verified by probe, `maraxiom` spec `261116_telemetry-config-layers` RESULTS rows 1-24): typed `userConfig` with `options`/`default`; saved in the user's `settings.json` under `pluginConfigs["<plugin>@<marketplace>"].options`; MCP gets `${user_config.KEY}`, hook processes get `CLAUDE_PLUGIN_OPTION_<KEY>` (saved only), the Bash tool gets none; `claude plugin configure --values-stdin` sets it.

**Evidence quality.** Rows marked *verbatim* quote a page fetched in full by a fetch agent (the quote is the page's text). Rows marked *agent report* come from a research agent that filed no structured record and, for opencode and pi, read pages through a summarising fetch: treat those as claims to re-check, not facts. Nothing here was probed against a running surface: probing needs each product's credentials, which this work does not copy. Everything is therefore **docs-only**.

## Probes (offline, scratch HOME, no credentials; real `~/.gemini` plugin directory checksummed unchanged)

**P1 (antigravity, `agy` 1.5.9, script `scripts/spikes/261117_cross_surface/probe_agy_variables.sh`).** An Antigravity plugin whose `mcp_config.json` declares `mcpServers.<s>.variables` installs **disabled**: `agy plugin install` printed "It is disabled until its MCP servers are configured: open /plugin and turn it on to fill them in", `agy plugin list --json` showed `enabled: false` (the same plugin without `variables` showed `enabled: true`), and `agy plugin enable` refused: "plugin "plugvars" cannot be enabled here: its MCP servers need configuring first; open /plugin in the interactive CLI and turn it on there to fill them in". `agy plugin validate --json` says: "server "srv" declares variables, so the plugin is off until the user fills them in; if config.json turns it on first, the server starts with the placeholders as written". Consequences: (a) declaring an Antigravity `variables` entry for an **optional** setting forces a setup step before the plugin works at all, which breaks the low-friction goal; (b) an unfilled placeholder reaches the server **literally** (`${NAME}`), so the resolver must treat an unexpanded placeholder as no opinion; (c) the variable cannot be marked optional (the documented fields are `name`, `title`, `description`, `link`).

**P2 (antigravity, same CLI, script `probe_agy_undeclared.sh`).** A plugin whose MCP `env` holds an undeclared `${X}` (no `variables`) installs **enabled** (`agy plugin list --json`: `enabled: true`). `agy plugin validate --json` warns: "server "srv": ${CISTERNAL_PLUGIN_OPTION_PROBE_SHADOW} isn't declared in "variables", so it's passed as is. The server inherits the agent's environment, so leave CISTERNAL_PLUGIN_OPTION_PROBE_SHADOW out of "env"". So on Antigravity the MCP server inherits the user's environment (a variable the user exports reaches it without any `env` entry), and an `env` entry with a literal placeholder would pass the placeholder as written. Runtime behaviour in a live session was not probed (needs credentials): docs-only.

**C1 (cursor, verbatim, https://cursor.com/docs/plugins/building, same text at /reference/plugins).** Only dashboard path stated: "Team admins set the actual values in the dashboard under **Plugins**" and "(at install time, or later via **Configure** on the plugin)"; the `variables` row: "users set them in the dashboard (**Plugins** → **Configure**)". Not found in any of the three pages: a way for a single user outside a team, a local file, a CLI or an environment route; what `${VAR}` becomes when unset; whether `default` is applied; whether a user-exported variable reaches the plugin MCP server. So Cursor's native path gives a solo owner nothing documented to set, and its unset behaviour is unknown.

**P3 (copilot, Copilot CLI 1.0.63 run through bun because the launcher needs `node`, scratch HOME and COPILOT_HOME; scripts `probe_copilot_plugin.sh`, `probe_copilot_control.sh`).** A plugin written the way cisternal's Copilot exporter writes it (array `command`, `env` with `${CISTERNAL_TELEMETRY_SHADOW:-}`) installs ("Plugin "cprobe" installed successfully."; `copilot plugin list` shows it), but `copilot mcp list` says "No MCP servers configured." The control, the documented string `command` plus `args`, gives the same result. So plugin MCP servers are not visible to `mcp list`/`get` outside a live session: whether Copilot reads the array form, and whether it expands `${NAME:-}` in a plugin server's env, cannot be probed offline without a model session (credentials). The CLI's own help says `--secret-env-vars` strips named variables "from shell and MCP server environments", which implies other variables reach them by default; the `/mcp add` docs say "The `PATH` variable is automatically inherited from your environment. All other environment variables must be configured here." The two do not agree; unresolved.

**C2 (copilot plugin docs, verbatim by a fetch agent, https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-plugin-reference and https://code.visualstudio.com/docs/agents/reference/agent-plugin-reference).** `mcpServers` is a "Path to an MCP configuration file (e.g., `.mcp.json`), or inline server definitions." The examples show `command` as a string with a separate `args` array (`"command": "npx"`, `"args": ["@company/mcp-server", "--plugin-mode"]`), never an array. Documented expansion in stdio plugin servers: `${PLUGIN_ROOT}` and `${PLUGIN_DATA}` (in args, env values and cwd); remote server values "are passed through literally, with no placeholder or environment-variable expansion"; no generic `${VAR}` expansion for stdio plugin servers is documented. Whether the plugin MCP config inherits the CLI's process environment: not found.

## What this changes for the design

1. Only Claude Code has a typed, locally readable saved value. A per-surface "saved-option reader" has nothing local to read for cursor (dashboard, team admins), antigravity (location undocumented) or copilot, jcode, opencode and pi (no declaration at all).
2. Rendering an option is not safe on the two surfaces that have a mechanism: Antigravity's `variables` make the plugin install disabled (P1), and Cursor's are a team-admin dashboard setting with undocumented unset behaviour (C1). Both rendered options were declined by the owner.
3. A pass-through of the environment variables into MCP `env` is not supportable by evidence on any surface: Antigravity's validator says leave the variable out because the server inherits the environment (P2); Copilot's plugin docs show no generic `${VAR}` expansion for stdio plugin servers and plugin servers cannot be inspected offline (P3, C2); pi and jcode are undocumented; opencode is second-hand. A literal placeholder reaching the server would shadow an inherited value.
4. What is supportable: the existing environment layer, the machine file and `mrx telemetry` are the cross-surface mechanism and the user should be told so (`cisternal telemetry where`), and a placeholder that a surface fails to expand ("passed as is", P2) must be read as no opinion, not as an invalid value that fails the setting closed.
5. A value that a surface supplies and that arrives as `CISTERNAL_TELEMETRY_*` would become the environment layer, which outranks `pyproject.toml`, Claude's saved option and the machine file. A future surface-native value therefore sits at the plugin-option position instead (owner decision D1 in the spec).

## Exporter side findings (check against docs; file as debt)

- opencode: the exporter writes the flat `mcp.<name>` form; the schema page marks it legacy in favour of `mcp.servers`.
- pi: `.pi/mcp.json` inside a package may not be loaded on `pi install` (documented MCP locations are `~/.pi/agent/mcp.json` and the project's `.pi/mcp.json`, after trust).
- copilot: `command` is emitted as an array; not yet checked against the docs.
- jcode: a `plugin.json` / `marketplace.json` that no documented loader reads.
- antigravity: the exporter's own docstring flags its MCP `env` passthrough as unconfirmed; docs disagree on the install path.
